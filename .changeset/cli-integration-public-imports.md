[feat] `astryx doctor integration validate` now warns, from source and without a build, when what an integration package tells apps to import cannot be imported, so `astryx integration check --strict` fails on it. Each is a warning, so `doctor integration validate` and a plain `integration check` keep their exit codes. It warns on a component doc's `import` or a template's public import whose subpath package.json `exports` does not declare (a missing key, a key whose only conditions an ES module import does not load, such as `require` or `types`, an `exports` that is a single string, a wildcard that does not match) or that names another package; a component example that imports a subpath the package does not declare or a name it does not export; a template source with no default export (`astryx template` still copies it, but its public import and anything that renders it get nothing); a template that imports a relative path outside the templates root, a path its own package or Core does not export, or a name its package does not export; a block whose `exampleFor` or `componentsUsed` names no component of the package or Core and is not imported by the template; and `@astryxdesign/*` peer ranges that are not semver ranges, and Core listed in `dependencies` instead of `peerDependencies`. Each warning names the fix, such as the exact `exports` entry to add. Only the declared subpath is judged, never the target file, so `exports` may point at build output that does not exist yet; wildcards and condition objects with `import` or `default` pass, a package with no `exports` keeps its deep paths to files it ships, and a CommonJS module is not judged for the names it exports.

`doctor integration validate` also lists, in a new `peerRanges` field (`{status: 'checked', findings}`), each `@astryxdesign/cli` or `@astryxdesign/core` peer range that excludes the CLI running or the Core installed, with its fix. These are listed only: they never count as warnings or fail `--strict`, since a package that pins its peers exactly while building on a newer release is correct.

`astryx integration add component` and `astryx integration add template` now add the new subpath when the package already has an `exports` map, as `integration add theme` does, inserting only that entry and leaving the rest of package.json byte for byte, and adding nothing when a wildcard already covers it. A package without `exports` is left as it is.
