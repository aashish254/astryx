[feat] `astryx doctor integration validate`, and so `astryx integration check --strict`, now checks from source, without a build, that what an integration package tells apps to import can be imported. It flags a component doc's `import` or a template's public import whose subpath package.json `exports` does not declare (a missing key, a key with only a `require` condition, an `exports` that is a single string, a wildcard that does not match) or that names another package; a component example that imports a subpath the package does not declare or a name it does not export; a template source with no default export (`astryx template` still copies it, but its public import and anything that renders it get nothing); a template that imports a relative path outside the templates root, a path its own package or Core does not export, or a name its package does not export; a block whose `exampleFor` or `componentsUsed` names no component of the package or Core and is not imported by the template; and `@astryxdesign/*` peer ranges that are not semver ranges, a CLI or Core peer range that excludes the CLI or Core in use, and Core listed in `dependencies` instead of `peerDependencies`. Each finding names the fix, such as the exact `exports` entry to add. Only the declared subpath is judged, never the target file, so `exports` may point at build output that does not exist yet; wildcards and condition objects with `import` or `default` pass.

`astryx integration add component` and `astryx integration add template` now declare the new subpath in package.json `exports`, as `integration add theme` does, creating the map when the package has none (keeping `main` as `.`) and adding nothing when a wildcard already covers it, so a fresh scaffold passes `integration check --strict` and `integration verify`.
