[feat] `astryx doctor integration validate` now warns, from source and without a build, when what an integration package tells apps to import cannot be imported, so `astryx integration check --strict` fails on it. Each is a warning, so `doctor integration validate` and a plain `integration check` keep their exit codes. It warns on a component's import (the doc's `import`, or the one the CLI derives when the doc has none) or a template's public import whose subpath package.json `exports` does not declare (a missing key, a key whose only conditions an ES module import does not load, such as `require` or `types`, an `exports` that is a single string, a wildcard that does not match) or that names another package; a component example that imports a subpath the package does not declare; and a template that imports a relative path outside the templates root, or a path its own package or Core does not export. Each warning names the fix, such as the exact `exports` entry to add. Only the declared subpath is judged, never the target file or the names it exports, so `exports` may point at build output that does not exist yet; wildcards and condition objects with `import` or `default` pass, an `import type` statement accepts a `types`-only entry, and a package with no `exports` keeps its deep paths to files it ships. What it cannot judge (in a package with no `exports`, a deep path into build output not built yet, such as `dist/`; a template import of Core when `@astryxdesign/core` is not installed beside the package) is listed, not warned on, in a new `publicImports` report on the validate result (`{status: 'checked', findings: [], unchecked: [{file, specifier, reason}]}`), which `integration check` counts as not compared. A package.json with no `name` gets only the checks that need none, and the report says the rest was skipped.
